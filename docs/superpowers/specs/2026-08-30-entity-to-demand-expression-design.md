# 产品实体到用户需求表达设计

日期：2026-08-30

## 目标

把 Product Hunt、GitHub 发现的产品/项目实体，转成有原文依据、可直接交给 Google Trends 查询的用户需求表达，同时保留原始实体作为独立候选。系统不从产品名臆测商业价值，也不把模型改写当成事实。

## 范围

- 输入：产品名、tagline、description、README、Issues/Discussions、SCYS 标题和正文。
- 输出：实体表达、需求表达、证据引用、表达类型、来源和置信度。
- 首批实现使用已有来源字段和本地规则；详情补全接口预留给 Product Hunt/GitHub，未获得正文时不生成需求表达。
- 不实现 Google Trends 自动调用，不修改来源认证和凭证存储。

## 处理流程

1. 归一化原始信号，识别产品实体与可用正文。
2. 从正文中识别用户任务、痛点、替代关系和新玩法四类证据。
3. 通过固定模板生成最多 3 个中文/英文搜索表达；每个表达必须绑定原文引用和来源 URL。
4. 将实体表达和需求表达放入同一表达簇，但保留 `kind`、证据等级和来源关系。
5. 候选排序优先需求表达，其次是有正文证据的实体；无正文单源实体只进入观察候选。
6. 报告展示“需求表达 → 来源实体 → 原文证据 → Google Trends 7d 链接”。

## 证据约束

- 没有正文引用的需求表达不得写入候选池。
- 模型或规则不得补充原文没有的受众、规模、收入和趋势判断。
- 单一产品名不能伪装成用户需求；SCYS 只能提供中文场景验证，不自动制造跨来源佐证。
- `partial`、`blocked`、`unverified` 保留为覆盖状态，不转化为零需求。

## 成本与降级

- 只对最近 7 天且排名靠前的最多 20 个实体做详情补全/表达抽取。
- 优先规则抽取；模型抽取作为可选增强，不可用时保留实体候选和原文。
- 所有抽取结果可通过 JSON 结构校验；不合格结果丢弃并保留失败原因。

## 验证标准

- 单源产品实体不会被直接标记为用户需求。
- 有明确任务/痛点原文的信号能生成需求表达并保留引用。
- 无正文或无可引用句子的信号不会生成需求表达。
- 需求表达在候选排序中优先于同源产品实体。
- 现有 200+ 测试、构建和来源状态行为不回归。
